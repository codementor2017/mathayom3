🧠 Lesson 4 — Variables, Logic, and Functions

⏱️ 100 minutes 📘 Indicator 1 🗓️ Semester 1 · Midterm 🎓 Grade 9

🧭 Lesson Opener

"When you tap the Calculate button on a calculator app, how does it know what to do? How does it know which numbers you typed? How does it decide what to show?"

Behind every app is a set of instructions — logic that tells the app what to do with the user's input. In this lesson, you will learn the three building blocks of app logic: variables, conditions, and functions. Once you understand these, you will be ready to code your first real app.

📖 1. Variables — The Memory of an App

A variable is a named container that stores a value. Think of it as a labeled box. You can put a number, a word, or a true/false value inside, and later ask the app to "look inside the box."

Example: in a BMI calculator, we need three boxes:

  • weight — stores the number the user typed.
  • height — stores the number the user typed.
  • bmi — stores the result after calculation.
Why variables matter: Without variables, the app cannot remember what the user entered. Variables let the app store, update, and reuse data.

📖 2. Conditions — The Decisions of an App

A condition lets the app make a decision. It asks a yes/no question and chooses what to do based on the answer. Conditions use keywords like if, else if, and else.

Example: in a BMI app, the app must decide the category:

  • if bmi < 18.5 → show "Underweight"
  • else if bmi < 25 → show "Normal"
  • else if bmi < 30 → show "Overweight"
  • else → show "Obese"

Only one branch runs — the app checks the conditions in order until one is true.

Tip: When writing conditions, always think of the edge cases. What if the value is exactly 25? What if it's negative? Good developers cover every possibility.

📖 3. Functions — The Workers of an App

A function is a named block of code that does one specific job. You "call" a function whenever you need it. This keeps code organized and easy to reuse.

In a BMI app, we might have two functions:

  • calculate_bmi(weight, height) — returns weight / (height × height).
  • get_category(bmi) — returns "Underweight", "Normal", etc.
Example in Python: 
def calculate_bmi(weight, height):
    return weight / (height * height)

def get_category(bmi):
    if bmi < 18.5:
        return "Underweight"
    elif bmi < 25:
        return "Normal"
    else:
        return "Overweight"

A function should do one job well. If a function tries to do too much, it becomes hard to test and fix.

📖 4. The Event-Driven Model — How Apps React

Mobile and web apps are event-driven. That means the app waits for the user to do something, then reacts. The three parts are:

  • Event — something the user does (tap, type, swipe, speak).
  • Trigger — the block that notices the event and starts the response.
  • Response — what the app does (show a result, play a sound, move a screen).
Example: In a BMI app:
Event: user taps "Calculate."
Trigger: the Button.Click block fires.
Response: the app reads weight and height, calls calculate_bmi, calls get_category, and displays the result.

🔍 Case Study — Logic Behind a Tip Calculator

A small restaurant wants an app that calculates tips. Here is how the logic is planned.

Variables:

  • bill — the amount on the receipt.
  • tip_percent — the tip percentage (10, 15, or 20).
  • tip_amount — the result of the calculation.

Function:

def calculate_tip(bill, tip_percent):
    return bill * (tip_percent / 100)

Conditions (to recommend a tip amount):

  • If service was "Excellent" → 20%
  • If service was "Good" → 15%
  • Otherwise → 10%

Event: user taps "Calculate Tip."

Response: app reads bill and tip_percent, computes tip_amount, and displays the total (bill + tip).

Reflect: What would happen if the app allowed a negative tip? How would you prevent that?

🛠️ Hands-On Task — Plan the Logic for Your App

Using your app idea from Lesson 2, plan its logic in your notebook.

  1. Variables: List all the values the app must remember (inputs + results).
  2. Conditions: List the decisions the app must make. Write them as if / else if / else.
  3. Functions: List one or two functions the app needs. For each, write its name, inputs, and output.
  4. Events: List the events the user will trigger (button taps, typing, etc.).
  5. Flow diagram: Draw a simple flowchart showing the flow from event → response.

When you finish, exchange notebooks with a partner and check each other's logic. Look for any missing edge cases.

🔑 Key Takeaways

  • Variables store data (like labeled boxes).
  • Conditions make decisions using if / else if / else.
  • Functions do one job and can be reused.
  • The event-driven model has three parts: Event → Trigger → Response.
  • Planning the logic before coding saves time and prevents bugs.
